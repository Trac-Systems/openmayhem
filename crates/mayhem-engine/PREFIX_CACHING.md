# Prefix caching and provider admission

LLM providers must initialize prefix reuse before advertising service. The shared vLLM adapter explicitly enables prefix caching and hybrid align mode, and validates the actual initialized setting. Its pinned vLLM 0.24 runtime receives the reviewed recurrent/speculative cache-boundary correction during setup. Before loading hybrid weights, the adapter resolves vLLM's attention backend and cache page size from model metadata. Prefill batch limits and positive long-prefill thresholds smaller than one cache block are raised to that block size; sufficient limits remain unchanged. Adjustments are logged as `prefix_cache_prefill_alignment` and do not require catalog edits or recalibration. The llama.cpp text adapter retains one private bounded prompt snapshot before the final prompt token; subsequent requests decode their uncached suffix and fresh final logits. Identical and extending prefixes can reuse recurrent/SWA state without rollback. Changed earlier tokens can require a cold prefill.

The live signed heartbeat includes `prefix_caching: true` only from an initialized supporting backend. Updated gateways reject generation routes with absent or false evidence; signed catalog output-token tariffs identify these routes, so changing heartbeat capability labels cannot bypass the requirement. This is signed runtime reporting under the existing provider trust model, not a new hardware proof against a malicious modified binary. Upgrade providers before gateways. Media and embedding routes are exempt. Other adapters that do not expose initialized support fail LLM startup admission.

There is no fleet-specific enable switch. For llama.cpp, `MAYHEM_LLM_PREFIX_CACHE_MAX_BYTES` controls the retained-state budget (default 8 GiB, minimum 64 MiB). Snapshots use private temporary files, on `/dev/shm` tmpfs on Linux. They are removed on replacement, model reload, and normal process exit. The model/context memory budget still applies. A snapshot larger than the budget is not retained. Abrupt host/process termination can leave private temporary files for normal host cleanup. Multimodal llama.cpp requests currently run through their existing fresh-context path; text prefix state is not applied to image/audio embeddings.

Cache hits are not guaranteed: changed prefixes, cache size, process restarts, scheduling to a different worker, and native rollback limits can cause misses. Input usage and signed billing remain full prompt-token counts; no cached-token discount or calibration/catalog identity change is introduced. Only token counts and cache storage sizes appear in diagnostics.

vLLM providers use a separate finite virtual-address allowance based on the machine's actual total RAM or known dedicated GPU memory, minus the reserve. Unified GPU probes can fall back to available RAM for their allocation pool; that fallback never becomes the virtual-address total. Available memory and existing claims still determine physical-memory admission and allocation. This prevents a restart after another model has loaded from shrinking `RLIMIT_AS` below CUDA reservations plus mapped weights. Linux cgroup containment, when available, continues to use the physical limit; the fallback enforces the separately reported address limit. A changed limit on model reload creates a new worker.

The chat gateway accepts OpenCode's `store: false` and optional string `prompt_cache_key` as client metadata. These do not enter the signed inference contract or change its fingerprint. Stored completions (`store: true`), malformed hints, and arbitrary unsigned attributes remain rejected. Prefix caching uses token identity and does not require a supplied cache key.

Validation includes initialized-config mismatches, signed heartbeat tampering/legacy evidence, every isolated-worker load and recovery, and native warm/cold output equivalence. Run `MAYHEM_PREFIX_CACHE_TEST_MODEL=/path/to/model cargo test -p mayhem-engine --features llama-cpp-cuda --test llama_prefix_cache -- --ignored --nocapture` on a compatible GPU. Fleet acceptance additionally uses actual OpenCode long-context follow-ups and tool calls with receipt provider verification.
